# T1054 owner-message admission: production seam still needed

The written five-way policy and pure `ownercomms.Classify` are **not** a production admission gate. Today `internal/server/chat.go` broadcasts an untagged assistant stream once its prefix cannot be `[silent]`; `ownercomms` is called only from tests. A mock that preclassifies a candidate proves suppression mechanics, not actual model compliance. Do not merge or achieve T1054 on that evidence.

## Safe seam proposal

1. **Capture request context** at the owner turn boundary: an opaque request ID, whether there is a currently unanswered owner question or status request, and which answer has already been emitted (including `toolUse` assistant text). Do not infer from candidate wording alone. Notifications remain owner-invisible inputs, not automatic owner messages.
2. **Structured admission before text:** change the overseer provider protocol to require a typed sideband `owner_admission` record **before the first assistant text delta** of every candidate owner response: category (owner-only unresolved decision / material new uncontained uncommunicated anomaly / direct answer / requested status / routine), evidence source IDs (owner request or incident), anomaly identity and containment/communication status, and an explicit `none` disposition. Validate evidence against the current owner request and durable incident/communication state. No synthetic free-text marker can authenticate this record.
3. **Hold the whole stream**, including pre-tool `toolUse` text and partial deltas, until that record is accepted. Routine emits no body (not even acknowledgment), only a terminal empty turn; a SEND category releases buffered deltas in original order and records the incident/request ID as answered only once. If a tool use resumes the same turn, the previous admission does not automatically license new prose: require a new candidate classification with current fulfilled-request state. Dedup incident identity, not prose.
4. **Unknown/missing/contradictory classification:** keep the owner-body buffer closed and route the undecided turn for investigation; log an explicit reason and preserve raw text for audit. Do not auto-convert unknown to routine or paint a fallback acknowledgment. A claimed new safety incident with incomplete evidence must be investigated urgently, not silently discarded; a live owner question must remain pending and re-pressured for an answer. A bounded timeout/failure and owner-visible failure indicator may require owner product-design approval; a hidden indefinite wait is not acceptable.
5. **Oracles:** model a provider text fragment arriving before the sideband (must not paint), owner answer and anomaly admitted with evidence, duplicate anomaly/fulfilled status suppressed even across tool boundaries, unknown held without loss, cancellation/restart replay without leaking held text. Observe a genuine owner turn on the development wire and viewport after activation; never inject fake reports into the running daemon.

This requires a Claudia/ACP envelope or equivalent trusted sideband and request/incident state that is not currently present on the stream. A daemon keyword heuristic or unconditional `[silent]` default cannot safely stand in for it: either would lose a fresh safety incident or an unanswered owner question. **Design/protocol integration is an open dependency, not implementation completed by the pure classifier.**
